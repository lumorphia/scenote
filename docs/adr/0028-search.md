# ADR-0028: 検索は Prismtone と同じ形で、1 つの欄の言葉をタイトル・タグ・地点から探し、索引はまだ作らない

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-18 |
| Deciders | t1nyb0x    |

## Context

S6c までで探せるのは、名前を正確に知っているタグ (`/tags/:name`)、利用者のページ、トップの地図の場所ごとの数枚だけだった。要件定義書 11 章はタグからの検索を求め、22 章は「高度な検索」を MVP から外している。相棒は、タイトル・タグ・地点で探せるようにすると決めた。入力の形は「1 つの欄と、地点・タグの絞り込み」を選び、画面は lumorphia/prismtone の検索 (`/posts`) と同じ形に揃えると決めた。

## Decision

- 写真を探すページは `/posts?q=&tag=&place=` (Prismtone と同じ URL。投稿詳細は `/posts/:id` のまま)。出るのは一覧と同じく公開の投稿だけ (`listable`)。結果の URL をそのまま共有できるよう、最初のページと地点の候補は SSR の loader で読む (ADR-0018)。結果は検索エンジンに載せない (`noindex`)
- `q` は空白 (全角も) で区切った言葉。言葉ごとに、タイトル、タグの名前、候補の地名、地域名、自由入力の場所のどこかに含むこと。全部の言葉がそろったものだけを出す (AND)。言葉は 5 つ、1 つ 50 文字まで
- 比べるときは両方を NFKC と小文字にそろえる (タグの `normalizeTag` と同じ)。投稿の側は `lower(normalize(coalesce(列, ''), NFKC))`、タグの名前は保存のときにそろえてあるのでそのまま。先頭の `#` は外す。LIKE の `%`・`_`・`\` は文字として扱う
- `tag` (タグの名前と一致) と `place` (候補の地点の id) は、言葉と組み合わせて絞る。`tag` は Prismtone と同じく繰り返せて、全部が付いているもの (AND、10 個まで)。API は `GET /api/posts` に `q` と繰り返しの `tag` を足しただけで、ほかの絞り込みと同じ口
- 画面の組み方は Prismtone の `/posts` と同じ: 見出し、言葉の欄と「検索 →」、絞り込み (広い画面は左に置いてすぐ当て、760px 以下はダイアログで「この条件で探す」まで当てない)、読んだ件数、いまの条件のチップ (押すと外れる)、当たらないときの案内。並び順は、Scenote に人気の指標が無いので新着順だけ
- トップとタグのページの欄は検索の欄にし、ヘッダーに「写真を探す」を置く。タグのページ (`/tags/:name`) と投稿詳細のタグのリンクはそのまま
- 本文は探さない (相棒が決めた範囲の外。長い文で当たりすぎ、個人の情報も入りうる)

### 索引を作らない理由と、作るとき

`pg_trgm` は、文字の扱いが `en_US.utf8` の DB (開発も本番の postgres イメージも既定はこれ) なら日本語にも効き、2 文字の言葉でも正しく当たることを確かめた。それでも今は作らない。

- 当たる場所が 5 か所 (うち 3 か所は別の表) の OR なので、1 列の索引では絞り切れない
- 2026-10-18 に開発機で測った。公開の投稿 5 万件と付いたタグで、よく当たる言葉は 19ms、どれにも当たらない言葉 (いちばん遅い、全部を見る) でも 92ms

公開の投稿が 10 万件を超えるか、検索の応答が遅いと分かったら、`pg_trgm` の GIN 索引を式 (`lower(normalize(coalesce(title, ''), NFKC))` など。`normalize` と `lower` は immutable) に作り、OR を UNION に分けることを考える。

## Consequences

### 良い点

- 1 つの欄で、タイトルを覚えていなくても場所やタグの言葉で見つかる。URL を共有できる
- 新しい表も索引も拡張も無い。マイグレーションが要らない

### 悪い点

- 「夕焼け」で「夕焼」のタグは当たらない (言葉が投稿の側に含まれることを見る)。ひらがなとカタカナ、送り仮名のゆれはそろえない
- 件数が増えると全部を見る検索が遅くなる。上の目安で見直す
