# ADR-0013: 撮影場所の候補は XIVAPI の地名から街・フィールド・宿屋・ハウジングエリアだけを持つ

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-12 |
| Deciders | t1nyb0x    |

## Context

要件定義書 10 章は、撮影場所を地域 → エリアの 2 階層で持ち、候補選択と自由入力の両方を受け、候補は XIVAPI の地名を同期して DB に持つとしている (投稿のたびに外へ聞かない。lumorphia/prismtone の ADR-0008 の考え方)。

XIVAPI v2 の TerritoryType は 1,290 行あり、地域 (PlaceNameRegion) と場所 (PlaceName) を持つ。用途 (TerritoryIntendedUse) ごとに、ID・討滅戦・イベント・ハウジングの屋内などが混ざり、同じ名前の版がいくつもある。地域が「？？？？」の行もある。

## Decision

- 候補は TerritoryType の用途が 街 (0)・フィールド (1)・宿屋 (2)・ハウジングエリア (13) のものだけ。地域の名前が決まっていない行は入れない。同じ場所 (PlaceName の row_id) は 1 つにまとめる。2026-10 の時点で 79 か所
- 地域 → 場所の 2 階層。場所の名前はゲームの地図の名前のまま (例: ラノシア → リムサ・ロミンサ：上甲板層)。日本語だけを持つ
- 候補に無い場所 (ゴールドソーサー、ID など) は自由入力で書く (50 文字まで)。投稿はどちらか一方だけを持つ
- worker の `place-sync` が週 1 回 (月曜 4:30) 同期する。同じ場所は名前を書き換え、無くなった場所は消さずに `retired_at` を付けて候補から外す (投稿が指しているので)。退いた場所は新しく選べないが、選んだ投稿には出し続ける
- XIVAPI が空を返したら、不調とみなして何も変えない (全部を退かせない)
- 開発と本番の最初の 1 回は `pnpm --filter @lumorphia-scenote/app places:sync` で入れる。E2E は外へ出ないよう、いくつかの地名を DB に直接入れる

## Consequences

### 良い点

- 候補が短く、選びやすい。ゲームの地図の名前なので、見れば分かる
- 投稿のたびに外へ聞かない。XIVAPI が止まっても、候補は前のまま使える

### 悪い点・受け入れるリスク

- ID・討滅戦・ゴールドソーサーなどは候補に無い。自由入力に頼る。使われ方を見て、用途を足すかを決める
- 街は区画ごとに分かれる (リムサ・ロミンサ：上甲板層・下甲板層)。要件定義書の例 (ラノシア → リムサ・ロミンサ) より細かい

### 追従して必要になること

- S6: 場所ごとの一覧 (エリア別ギャラリーは要件定義書 23 章の将来の拡張)
- 英語の表示が要るときは `Name@lang(en)` も同期する

## Alternatives

- 用途で絞らずに全部を候補にする: 1,000 を超え、同じ名前の版と内部の名前が混ざって選べない
- PlaceNameZone (例: リムサ・ロミンサ市街) をエリアにする: 要件定義書の例に近いが、フィールドでは地域と同じ名前になるものがあり、2 階層が崩れる
