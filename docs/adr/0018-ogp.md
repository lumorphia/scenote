# ADR-0018: OGP の画像は派生画像のジョブで作り、meta は load context で SSR する

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-17 |
| Deciders | t1nyb0x    |

## Context

要件定義書 16 章は、投稿の URL を X などに貼ったときに写真そのものが大きく出ること (summary_large_image) を求めている。9.1 章は、公開と限定公開は OGP を出し、非公開は出さないとしている。18.1 章は共有用の画像を 1200x630 前後、形式は対応状況に合わせて JPEG とする。

リンクのプレビューを作るクローラーは JavaScript を動かさない。今の投稿のページは、ブラウザが API を読んで描いているので、meta はサーバーで HTML に入れる必要がある。AGENTS.md は「SSR の loader から自分の API を呼ばない」と決めている (E2E は Fastify が https で受けるので、自分への https の接続に開発の CA が要る)。lumorphia/prismtone は loader から自分の API を呼んでいる。

## Decision

### 共有用の画像

- `image-process` が、検証と再エンコードを済ませた display から、中央を 1200x630 に切り抜いた JPEG (`ogp.jpg`) を作る。display・thumb と同じキーの頭に置くので、公開範囲を変えたときの移動 (`image-move`) と削除 (`image-delete`) にそのままついていく。保留した投稿では非公開の置き場所に置く (ADR-0014)
- 切り抜きは Scenote の見せ方なので、`@lumorphia/media` ではなく Scenote の `ogp-image.ts` (sharp) に置く。入力は media が作った display なので、検証とメタデータの除去は済んでいる

### meta

- サーバーは React Router の load context (`serverReadsContext`) に「投稿の OGP を読む関数」を渡す (`server/load-context.ts`)。投稿のページの loader はそれを呼ぶだけで、自分の API を HTTP で呼ばない
- load context のキーは、サーバーとビルドされたアプリが別々にモジュールを読み込んでも同じオブジェクトになるよう、`globalThis` の `Symbol.for` に 1 つだけ置く
- 共有できる投稿 (`domain/share.ts`) は、ログインしていない人に見える (`canView`) 公開・限定公開の投稿だけ。非公開・保留・作っている途中・退会中の人の投稿・無い投稿は OGP を出さない
- 検索エンジン: 公開の投稿は索引を許す。限定公開と、共有できない投稿は `noindex`
- タイトルが無い投稿は「〇〇 さんの写真」、本文が無ければ投稿者で説明を作る。説明は 1 行・120 文字まで

## Consequences

### 良い点

- 写真を中心にしたプレビューになる。画像は投稿と同じ置き場所にあるので、公開範囲の変更や削除で古い画像が残らない
- loader が HTTP を通らないので、E2E の TLS と関係なく SSR できる

### 悪い点・受け入れるリスク

- 横長に切り抜くので、縦長の写真は上下が切れる
- 公開範囲を変えて画像を移している数秒は、og:image がアプリの中継を指し、中継は ogp を返さない。その間に共有されると画像が出ない
- S6e より前に作った投稿には `ogp.jpg` が無い (本番に出る前なので作り直しはしない)
- 一覧・タグ・利用者のページには、まだ投稿ごとの OGP を出さない

## Alternatives

- loader から自分の API を HTTP で呼ぶ (Prismtone の形): 開発と E2E で自分への https に CA が要る
- Fastify の応答の HTML に meta を差し込む: React Router の外で HTML を書き換えることになり、壊れやすい
- 共有の時に画像を作る: 最初のクローラーが待たされ、作った画像の置き場所と消し方が別に要る
