# ADR-0021: 通報はログインした人から受け、運営は投稿を非表示にするか通報を退ける

| 項目     | 内容       |
| -------- | ---------- |
| Status   | Accepted   |
| Date     | 2026-10-17 |
| Deciders | t1nyb0x    |

## Context

要件定義書 26 章は、通報 (権利侵害、写り込んだ本人からの削除依頼、規約違反) と管理者の対応画面を MVP に含めている。19.2 章は、写り込んだ人からの削除依頼を通報で受けるとしている。通報はログインを求め、アカウントの無い人は問い合わせ先から受けると決めた (ADR-0019、相棒の判断)。運営が非表示にする状態 `hidden` は ADR-0020 で作った。

## Decision

### 通報する側

- ログインした人が、見えている (`canView`) 他人の投稿を通報できる。限定公開も URL を知っていれば通報できる。自分の投稿は通報できない
- 理由は `rights` (権利侵害)・`depicted` (写り込んだ本人からの削除依頼)・`terms` (規約違反) の 3 つ。詳しい内容は任意で 1000 文字まで
- 同じ人が同じ投稿を、対応待ちのまま二重に通報できない (部分ユニーク索引)。閉じたあとは、もう一度通報できる
- 1 分に 10 回まで。画面はボタンを押したときにログインを確かめ、ログインしていなければログインへ案内する

### 運営の側

- 対応待ちの通報を古い順に並べる。運営には通報した人を見せない (通報の行には残るが、一覧に出さない)
- **非表示にする**: 投稿を `hidden` にして画像を非公開の置き場所へ移し (ADR-0020 と同じ `hidePostTx`)、その投稿への対応待ちの通報を全部閉じる。記録は `post_hidden` を 1 行
- **退ける**: その通報だけを閉じる。投稿はそのまま。記録は `report_dismissed`
- **公開に戻す**: 非表示の投稿を一覧にし、公開に戻す。画像は公開範囲どおりの置き場所へ移す (`publishPostTx`)。記録は `post_restored`
- どれも理由が必須で、行を `FOR UPDATE` し、操作と同じトランザクションで記録する。もう片付いたものは `conflict`

### 消え方

- 投稿や通報した人が消えると、通報の行も消える (FK の cascade)。運営の操作は `admin_audit_logs` に残る (ADR-0019)

## Consequences

### 良い点

- 写り込んだ人の削除依頼を、運営がその場で非表示にできる。非表示は戻せるので、誤った対応をやり直せる
- 通報した人の名前が運営の画面に出ないので、運営が通報した人を見て判断を変えることが無い

### 悪い点・受け入れるリスク

- アカウントの無い人は通報できない。規約の問い合わせ先を案内する (S7d)
- 通報を濫用する人を止める仕組みは、回数の制限と二重の禁止だけ。濫用が続けば、S7c の利用制限で止める
- 通報した人に対応の結果を知らせない

## Alternatives

- ログインなしでも通報を受ける: 写り込んだ本人がすぐ通報できるが、スパムの対策 (Turnstile など) が要る。相棒の判断で採らない
- 通報が一定の数に達したら自動で隠す: 少数の利用者のうちは、狙った通報で投稿を消せてしまう
