# ADR-0016: 投稿一覧は公開の投稿だけを新しい順に、カーソルで読み、いちばん低い列に積む

## Context

要件定義書 12 章は、写真を中心にした、縦横比を保った一覧 (Pinterest や写真ギャラリーに近いもの) を求めている。表示はサムネイル、タイトル、投稿者、投稿日、タグで、メタ情報より写真を優先する。9.1 章は、一覧に出るのは公開の投稿だけとしている。

見られるかの判定は `canView` の 1 か所にまとめた (ADR-0012)。一覧は SQL で絞るので、同じ判定を SQL でも書くことになる。

## Decision

- `GET /api/posts` は、ログインなしで公開の投稿を新しい順 (公開日時、同じなら ID) に返す。1 ページは既定 24 件、上限 60 件。続きは前のページの最後の (公開日時, ID) を指すカーソルで読む (lumorphia/prismtone の browse と同じ形)。次が無ければ `nextCursor` は null
- 一覧に出す条件 (`browse.ts` の `listable`) は「画像ができている (`published`)・公開・投稿者が退会中でない」。これは `canView` でほかの人に見えて、しかも公開のものと同じ。2 つが食い違わないことを、状態・公開範囲・投稿者の組み合わせを全部作って突き合わせるテストで確かめる
- 並びに合わせて部分索引 `posts_public_list_idx` (公開日時と ID の降順、`published` かつ公開だけ) を置く。並びは NULLS LAST まで索引と揃える
- 画面はトップ (`/`)。ブラウザが API を読む (投稿のページと同じ。SSR の loader から自分の API を呼ばない)。写真は横幅をそろえた高さの比で、いちばん低い列に前から順に積む。列の数は画面の幅で 2〜5。CSS の段組み (columns) は使わない (縦に流れて新しい順が読みにくく、続きを足すたびに全体が組み替わるため)
- 続きは「もっと見る」のボタンで読む。無限スクロールにはしない

## Consequences

### 良い点

- 一覧と投稿の API で、見られるかが食い違わない (テストで固定)
- 続きを足しても、前の写真の位置が動かない

### 悪い点・受け入れるリスク

- 一覧は SSR しないので、検索エンジンやリンクのプレビューは一覧の中身を読めない。共有は投稿の URL と OGP (S6e) で行う
- 列に積むのは写真の比だけで決めるので、タイトルやタグの行の高さの分だけ列の下端がずれる

### 追従して必要になること

- S6c: タグ検索と利用者のページも同じ `listable` とカーソルを使う
- S6e: OGP

## Alternatives

- ページ番号 (offset): 投稿が増えると、読んでいる間にずれて同じ写真が 2 回出る
- CSS の段組み (columns): 実装は最小だが、上の理由で採らない
- CSS Grid の masonry: まだ主なブラウザで使えない
